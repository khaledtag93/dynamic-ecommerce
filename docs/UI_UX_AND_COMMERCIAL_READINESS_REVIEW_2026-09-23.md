## Admin UX: focused redesign without losing working behavior

The admin already has collapsible sidebar groups, a dashboard jump bar, a Growth subnavigation, a product save button at the top **and bottom**, and scroll-to-first-error behavior. Preserve those useful pieces. The problem is still information density, repeated explanation cards and very long editing contexts.

| Screen | Current structure | Recommended change | Acceptance check |
| --- | --- | --- | --- |
| Dashboard (`admin/dashboard.blade.php`, ~82 KB) | The first page contains an overview, decision summary, attention cards, workspaces, navigation guidance, filters, KPIs, watchlist, action center, trends, funnels and multiple lists before the end. A jump bar helps but does not reduce the amount to interpret. | Default to an operator view: 4–6 decision KPIs, exceptions requiring action, and recent orders. Put deeper revenue/marketing analysis in the existing Analytics/Growth destinations. Make date range and metric definition visible. | An operator can identify the next action and reach the relevant order/product in a few interactions; no repeated explanation of the same metric. Verify role-specific data visibility. |
| Product create/edit (`livewire/admin/product/product-form.blade.php`, ~81 KB; 1,400+ lines) | Basic details, pricing/stock, variant generation and rows, product relations, SEO and images live in one form. Save/error handling is present, but there is no persistent section navigator. | Add a section rail or tabs for Basics, Price & stock, Variants, Media, Related products and SEO, with completion/error indicators. Keep one Livewire state and existing save semantics initially; reveal advanced fields only when needed. Add a publish-readiness summary and Arabic/English content completeness check. | Switching sections does not lose unsaved values, upload state, variant edits or validation errors; errors open their section; saving still works once and both existing save controls remain accessible. |
| Branding (`admin/settings/branding.blade.php`, ~60 KB) | Theme, identity, many color controls, homepage CMS, banners, trust blocks, admin branding, image uploads and preview share one long form. | Group into separate focused workspaces or tabs (Identity, Storefront content, Banners, Theme, Media). | Analytics (`admin/analytics/index.blade.php`, ~69 KB) | Existing Overview/Growth/Offers nav helps, but the overview also adds many comparison, pattern, lane and explanation cards. | Put core definitions and 3–5 key outcomes first; progressively expose diagnostic charts and drilldowns. Order and product lists already have filters/pagination. | Simplify default navigation by task and permission; retain search/quick access but remove duplicated links and low-value status copy. Use the existing Growth page split as a practical pattern. Extract components and CSS/JS gradually; do not rewrite all screens or change product rules in one UI patch.

## Release gates and measurable success

1. **Trust/content gate:** inventory all published catalog/CMS/support/policy content; hide demo content; remove fabricated reviews and unsupported “best seller/free shipping/urgent” statements. These changes are a prerequisite to asking real customers to purchase.
2. **Security and transaction gate:** close explicit owner/Super Admin policy, credential rotation, shipping/tax decision, unpaid stock lifecycle and Paymob successful/failed/late/duplicate E2E tests. Preserve exact-commit QAS → visual review → Production dry-run → deploy → smoke/rollback workflow.
3. **Admin usability gate:** test the product form, order handling and branding tasks with realistic records in both languages at desktop and narrow widths. Each screen must keep state, show errors in context, and let staff finish its main task without searching through unrelated panels.
4. **Customer usability gate:** test homepage → search/category → product → cart → checkout → payment result → order support on mobile and desktop. Cover keyboard, visible labels, focus, failed validation, empty states and RTL. Do not run a real paid transaction without a controlled payment test plan.
5. **Measure rather than promise success:** establish trustworthy non-demo baselines for product-search use/success, product-to-cart rate, checkout start-to-completed/paid rate, failed-payment rate, stock discrepancy, return/support rate, and net margin. Observe LCP, INP and CLS at the 75th percentile by device once real traffic exists. Compare each focused change against its baseline and customer feedback.

### Suggested implementation order

- **Batch 0 — readiness (immediate):** authorization fix and regression coverage; remove synthetic social proof; prevent Production demo seeding; inspect/clean public test content and contact settings; verify what can be safely changed in QAS before any Production promotion.
- **Batch 1 — discovery and honest pricing:** working search; shipping/tax rules and checkout totals; correct free-shipping copy and best-seller eligibility.
- **Batch 2 — admin daily work:** product form sectioning/publish checklist, then order detail and branding workspaces, then a shorter operator dashboard. Keep each as a small QAS-reviewed increment.
- **Batch 3 — customer conversion:** product information hierarchy, homepage conditional sections, checkout labels/address reuse, then returns/reviews and measured experiments.
- **Batch 4 — technical foundation:** Laravel upgrade on its own branch, focused tests, performance assets and observability. Prioritize security support while keeping the change isolated from a simultaneous UI rewrite.

The business owner must supply real product data/images, support contact details, shipping zones/rates, actual tax treatment, return policy and Paymob account readiness. These are product inputs; the code audit cannot safely invent them. POS, SaaS, multi-warehouse and mobile remain outside the current phase.

## Research references for the acceptance checks

- [W3C form labels and instructions](https://www.w3.org/WAI/tutorials/forms/labels/) and [WCAG 2.2 quick reference](https://www.w3.org/WAI/WCAG22/quickref/) support persistent accessible labels, input purpose and keyboard/focus checks.
- [Google Web Vitals](https://web.dev/articles/vitals) defines LCP, INP and CLS and recommends assessment at the 75th percentile of visits.
- [Baymard checkout research](https://baymard.com/lists/cart-abandonment-rate) identifies unexpected costs, forced account creation and long checkout as common reasons for abandonment; use it as a hypothesis source, then measure Dynamic's actual funnel.
- [Laravel release support table](https://laravel.com/framework/docs/releases) confirms Laravel 10 security support ended on 2025-02-04 and Laravel 13 requires PHP 8.3. An upgrade still needs package compatibility and regression validation on QAS.
